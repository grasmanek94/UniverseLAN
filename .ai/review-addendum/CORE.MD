## Deeper lifecycle, callback and contract notes

### Exceptional initialization and recovery

The failure stages are distinct. Invalid/unavailable local configuration can fail before graph construction; DNS/host creation can fail after registrar/queue publication but before offline interfaces; a later interface allocation can leave earlier interfaces published; native thread creation can fail after construction and stdout replay. This is not one transactional Init. A blanket assertion that partial initialization is itself forbidden would conflict with the SDK. The defect in ADD-001 is the specific offline functionality the SDK promises, not the mere existence of partial state.

`reset()` calls `internal_reset()` before cleanup. For a config-construction failure it can retry the same fallible work. Use a no-allocation teardown primitive in a future lifecycle redesign rather than assuming the current reset is automatically appropriate in a destructor. Stale retained config across Shutdown and retry needs a documented reload policy; changing an INI after a failure is not currently a demonstrated automatic reload. No extra ID based only on preference for configuration reloading.

### Automatic destruction versus explicit reset — unresolved production reachability

The actual automatic order is definite: after `~InterfaceInstances` stops only the ENet Client, reverse member destruction removes `delay_runner`, then `notification`, then later `custom_networking`. A live WebSocket Channel borrows the registrar; its callback calls NotifyAll, which dereferences the registrar's borrowed queue. Channel destruction calls `client.stop()`, and IXWebSocket 12.0.1 closes and joins its thread while callbacks are still installed (`IXWebSocket.cpp:46–63,180–200,373–453`). Thus a live automatic owner teardown with an executing/message/close callback can reach already destroyed notification state. Explicit reset uses the opposite, safer dependency order.

This was **not promoted to a confirmed production ADD ID**. The inspected production owners are static and SDK documentation tells callers to perform Shutdown; ordinary properly completed explicit shutdown leaves these members empty. On Windows, CRT/DLL detach timing, loader-lock joins and process-exit worker termination further affect the actual observed failure. A local-owner destruction probe outside the loader lock would prove the internal ordering bug, but is not by itself proof that a supported production caller omits Shutdown. Coordinator should establish the supported unload/exit path and whether automatic RAII fallback is promised, then decide the appropriate severity/ownership. Do not assert that explicit reset's good ordering proves the destructor safe.

### Callback lifetime, reentrancy and exceptions

- The cancellation protocol has three phases to protect: pending operation storage, dispatch snapshot/admission, and active invocation. BASE-001's expanded pop-to-invoke example is deliberately different from BASE-002's same-type snapshot. Private auth sets, WebSocket listener fields and cloud captures require their owners' integration even after registrar tokens are fixed.
- Unregistering self without deleting a later listener does not invalidate the local snapshot's container iterators. Re-registering the same address requires generations to prevent confusing a new registration with an old queued event. Locking raw sets during copying is insufficient; holding a mutex across arbitrary callbacks creates a different reentrancy problem.
- `DelayRunner::Run` invokes a locally owned function. If a callback throws, the current function/snapshot unwinds, remaining listeners for that notification are skipped, and other queued functions remain available to a later pump. Immediate network dispatch also propagates callback exceptions: the deserialization catch in `MessageReceiver::ProcessEventFor` does not enclose Handle. Its outer packet guard still destroys the received packet during C++ unwinding.
- Request listeners already popped are not restored after a throw. A created callback throwing also prevents the entered notification of that response. SDK callback signatures inspected are not noexcept, but the inspected documentation establishes neither guaranteed continuation of sibling callbacks after an application exception nor a swallowing/rethrow policy. Record this as a policy/verification question, **not** a new proven SDK exception-contract defect. Scoped locks and owned callback-string storage unwind; no leaked lock is inferred merely from propagation.
- Recursive ProcessData can overwrite Chat's callback-only borrowed view before an outer callback resumes; inspected Chat code resets only on exception and does not restore an outer view. Baseline API-018 already treats supported nested-pump reachability as unresolved. No duplicate CORE finding. Queue concurrency also does not promise serialized callbacks when multiple pump callers run; establish the supported scheduling contract before assigning every concurrent-pump symptom a new ID.

### Request routing and trust boundaries

The owned routing switch forwards each declared specific-user request type to the expected implementation. The stronger correlation issue is downstream: the relay broadcasts sender-local chat request IDs, while the recipient's Chat pops a listener by that ID. Actual server/client source supports BASE-API-001 / BASE-SERVER-008; not a new root-handler defect. Requests are keyed per listener type, so using one creation request ID for created and entered callbacks does not collide in the registrar maps. Their **lifetime**, not map-key collision, is the BASE-001 extension.

No remote exploit is inferred merely because the LAN uses configured identity/shared authentication. ADD-003 is an operational collision enforced by the relay. Likewise, `EventConnect`'s peer address reads depend on ENet peer generation/lifetime; a copied raw ENetPeer pointer alone does not prove UAF. NET/SERVER own the reconnect/retirement analysis.

### Public ABI, configuration, stream and thread limits

Public exports use SDK reference/layout types and the inspected Windows call convention. The internal normalizer is not ABI-compatible by reinterpretation and is not used that way. GetError's always-null stub belongs to BASE-005; the `load()` zero stub has no newly established contrary contract. Old `InitLocal` peer-library-path behavior and ShutdownEx static preservation need backend-specific semantics rather than conjecture about proprietary internals.

Client ID/service authentication and UniverseLAN's own configuration search are deliberate emulator boundaries. README instructs use of project configuration; an ignored Galaxy configFilePath is not automatically proof that a UniverseLAN save should be written elsewhere. Android-only storagePath is not a Windows save-location control. In contrast, ADD-002 identifies explicit, relevant local-bind and thread-spawn controls and follows their actual consumers. Ignored allocator hooks remain a capability/accounting gap; no mismatched free was established.

Logger's per-record insertion is locked; its stream-state read is not. Atomic filename counter is useful. No Windows localtime race was inferred from POSIX/global-buffer behavior. Negative vsnprintf handling deserves validation, but `-1 + 1` is zero, not a huge vector allocation; mutable arguments/locale changing between sizing and formatting are not assumed ordinary well-formed concurrent logging. A fix should validate return values and retain a synchronized stream-state policy without inventing a new memory-corruption finding.

## Follow-up integration questions and verification priorities

1. **CORE + STORAGE:** Which offline interfaces must survive each Init failure stage? ADD-001 must preserve DLC/language while making `IsDlcOwned` safe if User was never created. Combine fault injection with BASE-005's modern/legacy error contract and BASE-006 stdout restoration; merely catching DNS failure is incomplete.
2. **CORE + NET + SERVER:** How is game-server identity allocated independently of the local player? ADD-003 requires two accepted sessions in one process and independent shutdown. Preserve relay uniqueness; fix BASE-004's packet role separately. Account for debug/config identity overrides without treating them as a general runtime-role solution.
3. **CORE + BUILD/SDK integration:** Implement or explicitly reject nondefault local bind/thread controls (ADD-002). Validate socket endpoint, hook setup and matched join/destruction with synthetic spies. Define allocator and static-preservation support before relying on dormant wrappers.
4. **CORE + API + STORAGE:** Keep cancellation records valid until invocation admission, including the two-stage CreateLobby result. Reconcile queued captures, snapshot removal, popped requests, auth sets, WebSocket listener fields and cloud workers. A queue-only token patch cannot fix all of these.
5. **Lifecycle coordinator:** Is graceful automatic owner destruction without explicit Shutdown supported? Prove the intended Windows exit/FreeLibrary path before promoting the reverse-order teardown investigation. Use a shared no-throw teardown primitive, and verify outside-loader-lock worker shutdown where that is the supported integration.
6. **Callback policy:** Are callback exceptions allowed to escape ProcessData, and must untouched specific callbacks survive? Is recursive pumping supported? Choose an explicit policy and test both immediate network and delayed delivery, including exception cleanup and outer Chat view restoration. Do not infer behavior solely from absence of noexcept.
7. **CORE diagnostics:** Validate BASE-009 exact log bytes and BASE-010 deterministic concurrent I/O failure. Test BASE-008 directly before integrating it, while keeping its dormant status out of ordinary production-crash totals.
8. **ABI/build:** Coordinator's prior successful builds do not exercise these new failure paths. When authorized, focused Windows probes at factory-era, early game-server, post-server-networking-removal and thread-factory SDK boundaries are more informative than repeating the same happy-path build.
