### [ADD-BUILD-001] Individual interceptor-mode testcase targets do not build or stage their runtime dependencies

- **Severity:** Medium
- **Confidence:** High for the target graph and resulting missing-runtime path; not runtime-reproduced
- **Category:** Build / runtime deployment
- **Location:** `Source/DLLs/CMakeLists.txt:153-183`, especially the three producer-only `POST_BUILD` copies at 168-182. Integration context: `Source/TestCases/CMakeLists.txt:57-81,100-127,145-181`.
- **Affected scope:** Windows, either x86 or x64, `BUILD_UNIVERSELAN_TEST_CASES=ON` and `BUILD_INTERCEPTOR=ON`, building one generated testcase target from a clean runtime output. Native SDK import/runtime artifacts and the separately managed test configuration are prerequisites of that optional mode, not files inspected in this review.

**Evidence**

This generator places the client at `bin/<version>/<config>/Galaxy[64].dll` and the interceptor alongside it as `GalaxyInterceptor[64].dll`. The testcase runtime layout is populated only as side effects of building the three production targets: the client becomes `bin/tests/<version>/<config>/RealGalaxy[64].dll`; the interceptor becomes that directory's `Galaxy[64].dll`; the server is also copied there.

The testcase target links the SDK header/dummy library, common tracing/version libraries and an external SDK import library (`TestCases/CMakeLists.txt:69-75`). Its own post-build command copies the official runtime to **`gog/RealGalaxy[64].dll`** when interception is enabled (100-117), plus an optional peer DLL (120-127). Neither that link closure nor any `add_dependencies` edge reaches the client, interceptor or server producers. Merely declaring those targets earlier in `Source/CMakeLists.txt` does not build them when another target is requested.

**Failure mechanism**

With a valid optional-test configuration and clean version-specific output, select only `zz-testcase-x64-1.152.11-SignInGalaxy` (or the equivalent generated x86 target). Its target closure can produce the EXE and stage `gog/RealGalaxy64.dll`, but none of this file's three production `POST_BUILD` commands runs. The executable's normal imported `Galaxy64.dll` name has no corresponding DLL beside it; the official DLL was intentionally staged under another path/name. Starting from the configured testcase working directory therefore fails DLL loading before the test can use the interceptor. A previous full build can mask this by leaving the required artifacts behind.

**Impact**

Building/debugging an individual optional test project is not self-contained and can fail despite that target's successful build. This is a dependency/staging defect within the existing ROOT/bin layout. It is not a new objection to source-tree outputs, a claim that normal non-interceptor tests lack SDK staging, or evidence that the baseline production builds failed.

**Possible solutions**

Add the missing production dependencies to each interceptor-mode testcase, or introduce a per-version/per-configuration staging target that depends on the three producers and owns the required copies. A producer-only post-build side effect is also fragile when previously staged files are removed without relinking the producer.

**Recommended resolution**

Make each interceptor-mode testcase depend on a versioned runtime-staging target, using target-derived file names and configuration paths, with `copy_if_different` for the client, interceptor and server. Preserve the existing `RealGalaxy`/interceptor/`gog/RealGalaxy` selection scheme. Leave the normal official-SDK testcase mode on its existing staging path.

**Verification**

Proposed only: inspect the generated dependency closure, then in a separately authorized disposable output build only the single testcase target above with the documented prerequisites supplied by its owner. Require the EXE, `Galaxy64.dll`, `RealGalaxy64.dll` and server beside it, and the official runtime under `gog/`; repeat the staging check for x86. Verify an individual testcase build restores a removed staged DLL even if the production link outputs are current. DLL presence/import-resolution checks suffice to establish this fix; no sign-in or external-service operation is necessary. No build, test, credential inspection or native-binary inspection was performed here.
